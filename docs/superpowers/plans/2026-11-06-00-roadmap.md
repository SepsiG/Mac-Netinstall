# mac-netinstall — Roadmap

Spec: `docs/superpowers/specs/2026-11-06-mac-netinstall-design.md`

The spec is split into sequential plans. Each plan produces working, tested software on its own.
Only Plan 1 is written in full detail now; each later plan is written (with the writing-plans
skill) right before it starts, because it depends on interfaces and findings from earlier plans.

| # | Plan | Output | Needs hardware/VM |
|---|------|--------|-------------------|
| 1 | Protocol core (`ni-proto`, `ni-sim`) | Sans-IO server session + device simulator, e2e tests | no |
| 2 | Network servers (`ni-net`, `ni-bootp`, `ni-tftp`) | Interface-bound UDP transport, BOOTP + TFTP servers, loopback tests | no |
| 3 | Assets (`ni-assets`) | Boot kernel extraction, NPK download/verify/cache, version resolution | no (network only) |
| 4 | Engine + CLI (`ni-engine`, `ni-cli`) | Multi-device orchestration, profiles, auto-repeat, usable CLI | no (first hardware test possible) |
| 5 | Reference capture + config modes | Linux VM with official `netinstall-cli` vs `ni-sim`; keep / no-default / empty config modes | Linux x86 VM |
| 6 | Tauri app + i18n (`app/`) | GUI (Svelte), EN + HU | no |
| 7 | CI + packaging | GitHub Actions (macos-14), `.dmg`, release notes | no |
| — | Hardware validation | Checklist per arch, pcap fixtures, UDP-vs-BPF decision | devices |

## Facts established during planning (2026-11-06)

Verified by static inspection of the official `netinstall-7.25.1.tar.gz` / `.zip` (nothing executed):

- **Boot kernels are embedded as plain ELF images** in both `netinstall-cli` (Linux, i386 ELF)
  and `netinstall.exe` (Windows PE); identical bytes (same SHA-256) in both. Size is exactly
  computable from ELF program/section headers; images are contiguous. Mapping:

  | BOOTP vendor class (opt 60) | ELF machine | Distinguishing marker |
  |---|---|---|
  | `Mips_boot` | 8 (MIPS) big-endian | — |
  | `MMipsBoot` | 8 (MIPS) little-endian | `mt7621` |
  | `Powerboot` | 20 (PPC) | `Linux version 5.x ` without suffix, `e300`/`mpc83` |
  | `e500_boot`, `e500sboot` | 20 (PPC) | `Linux version …-e500` |
  | `440__boot` | 20 (PPC) | `Linux version …-440` |
  | `ARM__boot` | 40 (ARM) | — |
  | `ARM64__boot` | 183 (AArch64) | — |
  | `tile_boot` | 191 (TILE) | — |

  Small `type=3` ELFs found inside kernels are vDSOs — skip them (only `e_type == 2`).
  Not ELF / out of MVP: `X86_64__boot`, `PXEClient` (x86), `ARM64UEFI__boot`.
  Plan 3 extracts from the Linux tarball (gzip+tar is simpler than PE).

- **Official protocol vocabulary** (strings in `netinstall-cli`): `DSCV OFFR YACK NACK STRT TERM WTRM FILE RETR PING PONG`.
  Official offer format is `OFFR\n%s\n%s\n%s\n` (three fields; pyNetinstall sends them empty),
  terminate is `TERM\n%s`, and besides `autorun.scr` it can send a `mode.scr` file; string `keep`
  is nearby. → Config modes keep / no-default / empty are encoded here; exact semantics are
  determined in Plan 5 by capturing official `netinstall-cli` talking to `ni-sim`.
- Official tool uses *raw* BOOTP and NETINSTALL sockets on Linux, with fallback to normal sockets.
  pyNetinstall works on real hardware with plain UDP broadcast, so Plan 2 starts with plain UDP.
- Devices send Netinstall frames with **source IP 0.0.0.0**; the server receives its own
  broadcasts, so filter by source MAC.
- pyNetinstall cannot run on macOS unmodified (Linux-only `SIOCGIFHWADDR` ioctl), so the
  "validate ni-sim against pyNetinstall" idea from the spec is replaced by: ni-sim is written from
  pyNetinstall's code, and validated against the official `netinstall-cli` in Plan 5.
- Toolchain: rustup stable (1.99.1) is installed in `~/.cargo/bin`, but MacPorts' Rust 1.71 comes
  first in `PATH`. Plan 1 Task 0 handles this.

## Open hardware checks (from Plan 1 review)

- **Same-seq de-duplication:** `ServerSession` re-sends unanswered frames with the same `seq`
  (pyNetinstall never does). Verify a real board ignores a duplicated chunk — send one chunk twice
  on purpose. If it does not de-duplicate, disable retransmits for chunk steps
  (`ni-sim` `SimConfig::dedup = false` test shows the corruption mode).
- **Replies after the last chunk:** we require two state-matched replies, the second `RETR`
  (mirrors pyNetinstall). Capture what a real board actually sends.
- **Seq wraparound:** plans over 65535 frames (~64 MiB) are rejected; verify on hardware before lifting.

## Plan 2 outline — Network servers

- `ni-net`: list interfaces (name, MAC, IPv4/mask, up) via `getifaddrs` (`nix` crate);
  `Transport` trait; macOS `UdpTransport` using `socket2` with `SO_BROADCAST`, `SO_REUSEADDR`/`SO_REUSEPORT`
  and `IP_BOUND_IF` (setsockopt level `IPPROTO_IP`, option 25) on a tokio `UdpSocket`.
- `ni-bootp`: parse BOOTP/DHCP requests (op, htype, chaddr, xid, option 60, option 93);
  reply with yiaddr from a MAC-keyed pool, siaddr = server IP, file = per-arch boot filename;
  handle both plain BOOTP and DHCPDISCOVER/REQUEST (OFFER/ACK); reply to `255.255.255.255:68`.
- `ni-tftp`: RFC 1350 RRQ, `blksize` (RFC 2348) and `tsize` (RFC 2349) options, per-transfer
  ephemeral socket, retransmit on timeout, read-only file map.
- Tests: codec unit tests with byte fixtures; loopback integration tests (client implemented in test).

## Facts established during Plan 2 (2026-11-06)

- Unprivileged processes can bind UDP 67, 69 and 5000 on macOS; no root needed for the servers.
- `IP_BOUND_IF` is `socket2::Socket::bind_device_by_index_v4` (socket2 0.6.5, feature `all`).
  A wildcard (`0.0.0.0`) socket bound to `lo0` still receives unicast to 127.0.0.1.
- `lo0` cannot send to `255.255.255.255` (`ENETUNREACH`), so broadcast replies cannot be
  tested on loopback: `ni_bootp::serve` takes the reply destination as a parameter.
- nix 0.31 `LinkAddr::addr()` does not check the address length; `ni-net` checks `alen() == 6`.
- No `Transport` trait yet: the runners take a `tokio::net::UdpSocket`. The engine (Plan 4)
  owns sockets; a trait is added only if a BPF transport is ever needed.
- Review fixes (2026-11-06): `BindOptions::reuse` defaults to **false** — listeners on :67/:69/:5000
  must not set `SO_REUSEPORT`, or they would silently share the port with another server that does;
  without it any holder is reported as `AddrInUse`. `recv_from` errors in both runners follow
  `ni_net::RecvErrorGuard` (ICMP errors, `ENOBUFS`, `EINTR`, … back off 20 ms and are reported at
  most once per second; other errors, or 100 transient errors in a row, end the server). The BOOTP responder serves direct-link clients only (relayed requests are
  ignored), NAKs requests for foreign addresses and quarantines a declined lease (only a MAC holding
  a lease, with option 54 naming us, can decline). Config rejects a pool outside the subnet, a pool
  with no usable address and a server IP that is the network/broadcast address.

## Open hardware checks (from Plan 2)

- Broadcast BOOTP reply out of an `IP_BOUND_IF` socket reaches the board (and only via that port).
- RouterBOOT TFTP client: which options it sends (`tsize`? `blksize`?), and that it boots with
  `honor_blksize = false` (default). Also check whether it retransmits RRQ.
- Whether RouterBOOT sends DHCP (option 53) or plain BOOTP, per arch; capture to pcap fixtures.
- **smips vendor class:** smips boards are assumed to send `Mips_boot` (mapped to `BootArch::Mips`);
  unverified — capture option 60 from a real smips board.
- **Option 60 exact bytes:** capture the raw vendor class bytes per arch (trailing NUL? padding?).
  We strip trailing NULs/whitespace and otherwise match exactly.
- **DATA source IP:** transfer sockets now bind `server_ip:0` so DATA comes from the address the
  RRQ was sent to; check whether RouterBOOT rejects DATA from any other source IP (and port rules).
- **`bootpd` / launchd `tftpd` reuse behaviour:** check whether macOS `bootpd` (Internet Sharing)
  and the launchd `tftpd` set `SO_REUSEPORT`, and that our no-reuse listeners on :67/:69 report
  `AddrInUse` while they run.

- Downloads: `https://download.mikrotik.com/routeros/<ver>/netinstall-<ver>.tar.gz` and

- Kernel extraction per the table above; cache in `~/Library/Caches/<bundle-id>/<version>/`.

## Facts established during Plan 3 (2026-11-06)

- Version check: `https://upgrade.mikrotik.com/routeros/NEWESTa7.<channel>` for `stable`,
  `long-term`, `testing` and `development`; body `<version> <unix time>\n`
  (e.g. `7.25.1 1793623193`). `testing` equals `stable` while no rc is out. Unknown channel → 404.
- Downloads (`https://download.mikrotik.com/routeros/<ver>/…`): `netinstall-<ver>.tar.gz`,
  `<name>-<ver>-<arch>.npk` (main package `routeros`; the old `routeros-<arch>-<ver>.npk` order
  serves the same file; `routeros-<ver>.npk` without arch is x86), `all_packages-<arch>-<ver>.zip`.
  Extra packages are also published one by one under the same name pattern. Missing files → 404.
- Checksums: `<file>.sha256` (`sha256sum` format) is **required from 7.15 on** (7.15 final
  included; its betas/rcs are treated as older): a missing one is `checksum_missing`. Older
  versions may or may not have one (7.14.3 has one, 7.12.1 and older answer 404); without one they
  are accepted on size + NPK checks with `published_checksum: false`. A checksum that is present is
  verified for every version (`checksum_mismatch`). (The earlier "7.16.2" and "7.14 → 404" were
  wrong generalisations.)
- NPK header: magic `1E F1 D0 BA` + `u32` LE length; file size is always length + 8 (7.1 … 7.25.1).
- The extra-package list comes from the zip's central directory via `Range: bytes=-65536`
  (the server answers 206); no need to download the zip.
- reqwest 0.13's `rustls` feature uses aws-lc-rs and `rustls-platform-verifier` (macOS trust
  store). reqwest 0.13 needs Rust 1.85 and sha2 0.11 needs 1.88, so the workspace MSRV is 1.88.
- 7.25.1 kernels carve to: mips 5256784, mmips 5358860, powerpc 5486936, e500 6119156,
  ppc440 5709072, arm 3501676, arm64 7838328, tile 4680160 bytes (SHA-256s in
  `crates/ni-assets/tests/network.rs`).

## Plan 3 review outcomes (ni-assets)

- **Concurrency:** no global lock any more. Each target (package file, a version's kernel set,
  a package list, a local file) has an in-process async lock plus an exclusive `flock` on
  `<root>/.locks/<dir>-<name>.lock`, so several `Assets` (and processes) can share one cache root;
  the cache is re-checked after taking the lock. Cached reads (`local_file`, cached kernels and
  package lists) never wait for downloads. Index changes are read-merge-write under an index lock.
- **Verification:** downloads go to unique `<file>.<pid>.<n>.part` files (`create_new`); the bytes
  are read back from disk and must match the stream hash (`disk_mismatch`) and the published
  checksum. Stale part files (> 1 h, target not locked) are removed by `Assets::new` and by
  `clear_downloads`. Renames are followed by a directory `fsync`.
- **HTTP:** redirects only to `https`, or to plain `http` on the same host and port
  (`redirect_refused` otherwise). A user-configured plain-HTTP mirror has no transport integrity;
  only the checksums (≥ 7.15) and NPK checks protect it. Ranged reads check `Content-Range`; a server
  ignoring `Range` is accepted only for files ≤ 4 MiB.
- Open follow-up (not done): re-validate cached entries of ≥ 7.15 that were stored with
  `published_checksum: false` when the network is available.

## Open hardware checks (from Plan 3)

- Exact `arch` strings in the Netinstall hello per device family. `PkgArch::from_device_arch`
  accepts `arm`, `arm64`, `mipsbe`, `mmips`, `smips`, `ppc`/`powerpc`, `tile` (case-insensitive);

- Each carved kernel boots its family; especially the PowerPC split (generic / e500 / 440 by the

## Plan 4 outline — Engine + CLI

- `ni-assets` API as used by the engine (changes from the Plan 3 review):
  - `Assets` is shareable (`Arc`) and needs no external serialization; cancelling a call is safe.
  - `Assets::cached_versions()` → versions with a complete cached kernel set (offline fallback).
  - `HttpConfig::download_timeout` (overall per-download limit, default 30 min) next to
    `read_timeout`.
  - Local file names are lowercased: `LocalFile::name` is the lowercase file name, and that is the
    name the device receives (e.g. `Setup.RSC` becomes `setup.rsc`); `local_file(name)` matches
    regardless of case (APFS is case-insensitive). Names longer than `MAX_LOCAL_NAME` (200 bytes)
    are `unsupported_local_file`.
  - `HttpConfig::download_timeout` defaults to 30 min per file; that may be too short on very slow
    links (the ~46 MB tarball needs > 26 KB/s), so the engine should expose it as a setting.
  - New error codes the UI must translate: `timeout`, `redirect_refused`, `checksum_missing`,
    `disk_mismatch`, `cancelled`, `local_not_file`.
  - `Assets::new` stays synchronous; inside a runtime its stale-part cleanup runs as a background
    blocking task.
  - `Version` orders semantically (`7.9 < 7.25`, `7.26beta5 < 7.26rc1 < 7.26`).

- tokio runtime; one task owns transport + BOOTP + TFTP + all `ServerSession`s (demux by src MAC).
- Event stream (`tokio::sync::broadcast`) with codes + params (no localized text).
- Profiles (JSON in Application Support), concurrency limit, auto-repeat with cooldown.
- Preflight checks (interface IP in pool subnet, port conflicts e.g. `bootpd`, assets ready).
- `ni-cli` with `clap`; first real-hardware test as soon as a device is available.
- Runner APIs needed by the engine (from the Plan 2 review):
  - query and modify leases and the arch → boot-file map while the BOOTP runner is running
    (today both are fixed at `BootpResponder::new`);
  - a MAC allow/deny policy hook for BOOTP/TFTP: post-flash cooldown (do not re-boot a device that
    was just flashed) and a concurrency limit;
  - TFTP progress events (`Transfer::acked_bytes`, throttled), not only start/complete/fail;
  - IP → MAC correlation, so a TFTP peer (IP only) and the Netinstall session (MAC) can be matched
    to the BOOTP lease;
  - bounded or rate-limited event channels instead of `UnboundedSender` (a flood of junk
    datagrams must not grow memory without limit);
  - interface type info in `ni-net` (Ethernet vs Wi-Fi / `awdl` / `utun` / bridges) so the UI can
    hide interfaces that cannot boot a router.
- Preflight: check `TftpConfig { server_ip, interface }` and `BootpConfig::server_ip` are consistent
  (the IP is configured on that interface, listeners bound to the same interface).

## Facts established during Plan 4a (2026-11-06)

- Runner APIs used by the engine: `ni_bootp::serve_shared` + `BootpHandle` (`set_boot_files`,
  `set_policy(MacPolicy)`, `lease_of`, `mac_of`; the policy is asked only for supported RouterBOOT
  vendor classes, a refused MAC is `IgnoreReason::Denied`) and `ni_tftp::serve_watched` (file map
  from a `watch` channel, `TftpEvent::Progress` every 64 KiB). Both use bounded channels with
  `try_send` (events are dropped when the engine is behind; capacity 256 each). The old `serve`
  functions are unchanged.
- There is no TFTP MAC policy: the cooldown / only-MAC gate sits at BOOTP (no lease, no boot file)
  and at the Netinstall hello. The concurrency limit (default 4) counts preparing + flashing
  devices only; BOOTP and TFTP serve every device the gate allows.
- `ni-assets` futures were not `Send` (`Http::download` held a `&dyn Fn(AssetEvent)` across
  `.await`); fixed with a `+ Sync` bound and a compile-time test. Its test fixtures are exported
  behind the `testing` feature (`ni_assets::testutil`, never for shipping builds).
- `ni_net::Interface` has `kind` (`InterfaceKind`, from `sdl_type`, name prefixes and
  SystemConfiguration's interface type — Wi-Fi and Ethernet are both `IFT_ETHER`) and
  `display_name` (e.g. `Thunderbolt Bridge`, `Ethernet Adapter (en2)`). New dependency
  `system-configuration` 0.8.0. On the development Mac (macOS 27.0.1) `anpi*` (Apple internal),
  `ap1` (Wi-Fi AP, unknown to SystemConfiguration), `awdl0`, `llw0`, `nan0` exist besides `en*`.
- MAC masking (macOS 27, verified on the development Mac): macOS
  reports `02:00:00:00:00:00` as the link-layer address of every interface to some processes.
  It depends on the process's code signature, not on the API: ad-hoc *linker-signed* binaries
  (everything `cargo build` produces) get the placeholder from `getifaddrs` **and** from the
  routing sysctl `NET_RT_IFLIST`, and so do their children (`ifconfig` started from a test
  binary prints it too). Python.org's (Developer ID) Python and an ad-hoc binary re-signed with a
  reverse-DNS identifier (`codesign -s - -i com.example.x`) got real MACs from both APIs; one
  signed with an *Apple Development* certificate was still masked — so the shipped app's
  signing must be re-checked. IOKit's `IOMACAddress` (on `IOEthernetController`) is never
  masked. Fix: `ni_net::list_interfaces` treats `02:00:00:00:00:00`/all-zero as unknown and, for
  non-Wi-Fi interfaces, falls back to the IOKit hardware address (`ni_net::hardware_addresses`).
  Wi-Fi stays unknown when masked: with a private Wi-Fi address (rotating) `en0`'s address in use
  differs from the hardware one and can change. The engine refuses to start without a known MAC
  (`no_mac`) instead of sending frames from the placeholder (it uses the interface MAC as the
  source MAC of its Netinstall frames and to drop its own broadcasts; two Macs would collide).
  `ni-net/tests/mac_vs_ifconfig.rs` checks the result against `ifconfig`/`ioreg`.
- End-to-end tests run the real engine on `lo0` with ephemeral ports (`Ports`) against
  `ni_sim::lan::SimLan` (BOOTP + TFTP + `DeviceSim` per MAC, mute/reset fault injection). On
  loopback the TFTP client's address is not its lease, so `kernel_serving` is not observed there;
  IP → MAC lookup is tested in `ni-bootp/tests/shared.rs`.
- Engine events are JSON objects tagged by `event` (`started`, `kernels_ready`, `download`,
  `discovered`, `device`, `ignored`, `warning`, `error`, `stopped`); device states are tagged by
  `state` and flattened into the `device` event. Failures are `{code, params}`; a `detail` param is
  an English diagnostic for logs only.
- Offline start: if the profile's version cannot be resolved, the newest fully cached kernel set
  is served (`kernels_offline_fallback` warning). **Superseded by the Plan 4 review:** only the
  version the channel last resolved to is used (see below).

## Open hardware checks (from Plan 4a)

- **MAC address visibility:** answered — macOS masks it by code signature, see the MAC masking
  note above (IOKit fallback in `ni-net`). Still open: re-check with the signed app bundle, and
  whether a device accepts frames whose source MAC is not the interface's (e.g. an adapter with a
  custom address, where IOKit's hardware address is not the one in use).
- Netinstall over `IP_BOUND_IF`: our broadcasts to `255.255.255.255:5000` from a socket bound to
  `0.0.0.0:5000` reach the device, and its frames (source IP `0.0.0.0`) reach us.
- Cooldown default (5 min) against the real reboot time, and whether a flashed device netboots
  again at all (RouterBOOT boot order) — the cooldown must cover that window.
- Unplugging the USB Ethernet adapter during a run gives `link_down` (`interface_missing`) within
  ~2 s and `interface_gone` after the 10 s grace period; plugging it back in within the grace
  period gives `link_up` and devices are served again — this relies on the re-attached adapter
  keeping its interface index (otherwise `interface_gone`, `reason: index_changed`).
- **Recv errors on `IP_BOUND_IF` sockets when the interface vanishes:** an unplugged adapter could
  make the BOOTP/TFTP/Netinstall `recv_from` fail with a non-transient error and exit a runner
  with `runner_failed` before the 10 s grace period runs out — check what the sockets report.
- **USB adapter re-attach keeps its interface index:** otherwise `interface_gone`
  (`reason: index_changed`) is immediate on re-plug instead of a `link_up`.
- **Manual IPv4 without carrier (the link watchdog relies on it):** confirm on the USB/Thunderbolt
  adapter that macOS removes the manual address when the cable is pulled (or the router reboots)
  and restores it with the carrier; that our wildcard + `IP_BOUND_IF` listeners keep working
  afterwards without a rebind; how long the address takes to come back after the carrier; and
  that `IFF_RUNNING` really is no carrier indication there (on the development Mac, cable-less
  `en2`/`en3` report `RUNNING` with `status: inactive`).
- Local Network permission: what a send fails with before the permission is granted (CLI run from
  Terminal vs. the app), and that it shows up as `send_failed` (`service: netinstall`, rate
  limited) / `bootp_send_failed` / `recv_error` warnings.

## Plan 4 review outcomes (2026-11-06)

- **Link flaps are not fatal.** macOS removes a manually configured IPv4 address while an
  Ethernet interface has no carrier — with a direct cable on every device swap and router reboot.
  The watchdog (`EngineConfig::link_check`, 2 s) now reports a missing carrier / server IP once as
  `warning`/`link_down` (`reason`: `no_ip`, `no_carrier`, `interface_down`) and `link_up` when it
  is back; the engine keeps running and sessions in flight fail by their own timeouts. Only an
  interface missing from the list for `interface_grace` (10 s), or back under another index, is
  `error`/`interface_gone` (the engine stops). `IFF_RUNNING` is not a carrier indication on
  macOS (cable-less ports report `RUNNING`), so the missing address is the main signal.
- **Starting without link:** with `server_ip` (and `netmask`, default /24; CLI `--server-ip`,
  `--netmask`) configured, `start` works while the interface has no address and reports
  `link_down`. No rebind is needed when the link returns: the listeners bind `0.0.0.0` with
  `IP_BOUND_IF` (an interface index), which needs no address — verified: bind succeeds, sends fail
  with `ENETUNREACH`, binding the missing address itself fails with `EADDRNOTAVAIL`. Preflight
  reports the missing link/address as a warning then. The interface list is injectable
  (`InterfaceSource`) so all this is tested on `lo0` with a fake list.
- **Offline installs never change version:** `ni-assets` remembers each channel's last resolution
  (`<cache>/channels.json`, read-merge-write under a lock file, atomic rename). Offline, kernels
  and preparations fall back only to that version (kernels only if its set is cached), otherwise
  `kernels_unavailable` / `assets_failed`. `preparing` (once known) and `flashing` states and the
  snapshot carry the install `version`. A profile whose version differs from the served boot
  kernels is `profile_version_mismatch` (the device already booted that kernel).
- **Failed devices that netboot again** (a new BOOTP request, e.g. after a power cycle) are reset
  to `bootp_seen` and, with auto-repeat or an assigned profile, flashed again without `retry`.
  A **done** device is served again only after its cooldown *and* a new BOOTP request; stray
  hellos are `ignored`/`awaiting_bootp`. The cooldown is at least 30 s (`invalid_cooldown`).
- Netinstall send failures are `warning`/`send_failed` (`service`, `count`, `detail`), at most once
  per second, not while the link is down. Only the engine task owns the event `Sender` (handles
  hold a `WeakSender`), so a dead engine closes the stream (`engine_gone`). `stop` waits (≤ 2 s)
  for aborted runner tasks, so stop → start on fixed ports does not race (the race was not
  reproducible on loopback; the 20× stop/start test guards it). `ignored` rate-limit entries and
  expired cooldowns are pruned; the device map is capped at 1024 (oldest done/failed first, never
  active ones). `flash` keeps a queued device's place; turning auto-repeat off dequeues devices
  queued only by it.
- Preflight: `default_route` warning when the interface carries an IPv4 default route (probably a
  real LAN; read from `netstat -rn -f inet`), `pool_includes_reserved` for a pool containing the
  network/broadcast address, and `ni-bootp`'s own validation (`invalid_network`).
- CLI: while a device is being flashed the first Ctrl-C only warns, a second within 5 s aborts;
  exit 130 if stopped while a device was active (`cancelled` devices count); when `--count` is
  reached auto-repeat is turned off and devices still being flashed are waited for (their outcome
  counts); single-device runs' exit code follows the target only; lag is made up for from the
  snapshot; `--json` errors also go to stdout as `{"event":"error","code",...}` and the Ctrl-C
  notice as `{"event":"warning","code":"interrupt_pending",...}` — every JSON object the CLI
  prints is tagged by `event`, like engine events; the testing flags that redirect downloads or
  frames need `NI_CLI_TESTING=1`.
- A server IP that never comes back (link up, other addresses such as a 169.254 one, but not
  ours, for 3 watchdog checks ≈ 6 s) is `error`/`server_ip_not_on_interface` with the actual
  `addresses`, and the engine stops.

## Facts established during Plan 4b (2026-11-06)

- `ni-cli` (clap 4.6.7, MSRV 1.85; tracing-subscriber 0.3.23 + tracing-appender 0.2.5) logs to
  `~/Library/Logs/io.github.sepsig.mac-netinstall/ni-cli.<date>.log` (daily, 7 kept; `--log-level`

## First hardware test (with ni-cli)

1. Mac with a USB/Thunderbolt Ethernet adapter, static IPv4 (e.g. `192.168.88.1/24`), Internet
   Sharing off; `ni-cli interfaces` shows it as `ethernet`. Without a cable the address is gone;
   pass `--server-ip 192.168.88.1` to start anyway.
2. `ni-cli preflight --iface en7 --profile <name>` passes (no `port_in_use`).
3. `ni-cli assets fetch --version stable --arch <arch>` while online.
4. `ni-cli --log-level debug flash --iface en7 --version stable`, then power the board with the
   reset button held until it netboots (or `system routerboard settings set boot-device=try-ethernet-once-then-nand`).
5. Capture with `sudo tcpdump -i en7 -w first.pcap port 67 or port 68 or port 69 or port 5000`
   and keep the log; if a chunk step stalls, repeat with `--retransmits 0`.

## Plan 6 outline — Tauri app (GUI API needs from the Plan 4 review)

The engine API is enough for the CLI; the GUI needs more control at runtime:

- `set_active_profile(profile)` while running: re-selects (downloads) the boot kernels for the new
  version, and must report a visible "running but no kernels" state in between (today only
  `kernels_unavailable` / `kernels_ready` events exist; the snapshot has just `kernel_version`).
- `set_only_mac(Option<Mac>)`, `set_max_parallel(n)`, `set_cooldown(d)` (≥ 30 s) without a restart.
- Per-device `cancel(mac)` (abort one session: `failed`/`cancelled`) and `forget(mac)` (drop a
  device from the map and its cooldown).
- Snapshot additions: the resolved install `version` per device (done in the Plan 4 review),
  kernel download/ready state (version, progress, error), per-device timestamps (first seen, last
  change) and attempt count — the attempt count also lets a lagging client tell "finished twice"
  from "finished once".
- `link_down` / `link_up` warnings drive a link indicator; `send_failed` with `EHOSTUNREACH`
  before the first successful send most likely means the Local Network permission is missing.
