# mac-netinstall — Roadmap

Spec: `docs/superpowers/specs/2026-11-06-mac-netinstall-design.md`

The spec is split into sequential plans. Each plan produces working, tested software on its own.
Only Plan 1 is written in full detail now; each later plan is written (with the writing-plans
skill) right before it starts, because it depends on interfaces and findings from earlier plans.

| # | Plan | Output | Needs hardware/VM |
|---|------|--------|-------------------|
| 1 | Protocol core (`ni-proto`, `ni-sim`) | Sans-IO server session + device simulator, e2e tests | no |
| 2 | Network servers (`ni-net`, `ni-bootp`, `ni-tftp`) | Interface-bound UDP transport, BOOTP + TFTP servers, loopback tests | no |
| 3 | Assets (`ni-assets`) | Boot kernel extraction, NPK download/verify/cache, version resolution | no (network only) |
| 4 | Engine + CLI (`ni-engine`, `ni-cli`) | Multi-device orchestration, profiles, auto-repeat, usable CLI | no (first hardware test possible) |
| 5 | Reference capture + config modes | Linux VM with official `netinstall-cli` vs `ni-sim`; keep / no-default / empty config modes | Linux x86 VM |
| 6 | Tauri app + i18n (`app/`) | GUI (Svelte), EN + HU | no |
| 7 | CI + packaging | GitHub Actions (macos-14), `.dmg`, release notes | no |
| — | Hardware validation | Checklist per arch, pcap fixtures, UDP-vs-BPF decision | devices |

## Facts established during planning (2026-11-06)

Verified by static inspection of the official `netinstall-7.25.1.tar.gz` / `.zip` (nothing executed):

- **Boot kernels are embedded as plain ELF images** in both `netinstall-cli` (Linux, i386 ELF)
  and `netinstall.exe` (Windows PE); identical bytes (same SHA-256) in both. Size is exactly
  computable from ELF program/section headers; images are contiguous. Mapping:

  | BOOTP vendor class (opt 60) | ELF machine | Distinguishing marker |
  |---|---|---|
  | `Mips_boot` | 8 (MIPS) big-endian | — |
  | `MMipsBoot` | 8 (MIPS) little-endian | `mt7621` |
  | `Powerboot` | 20 (PPC) | `Linux version 5.x ` without suffix, `e300`/`mpc83` |
  | `e500_boot`, `e500sboot` | 20 (PPC) | `Linux version …-e500` |
  | `440__boot` | 20 (PPC) | `Linux version …-440` |
  | `ARM__boot` | 40 (ARM) | — |
  | `ARM64__boot` | 183 (AArch64) | — |
  | `tile_boot` | 191 (TILE) | — |

  Small `type=3` ELFs found inside kernels are vDSOs — skip them (only `e_type == 2`).
  Not ELF / out of MVP: `X86_64__boot`, `PXEClient` (x86), `ARM64UEFI__boot`.
  Plan 3 extracts from the Linux tarball (gzip+tar is simpler than PE).

- **Official protocol vocabulary** (strings in `netinstall-cli`): `DSCV OFFR YACK NACK STRT TERM WTRM FILE RETR PING PONG`.
  Official offer format is `OFFR\n%s\n%s\n%s\n` (three fields; pyNetinstall sends them empty),
  terminate is `TERM\n%s`, and besides `autorun.scr` it can send a `mode.scr` file; string `keep`
  is nearby. → Config modes keep / no-default / empty are encoded here; exact semantics are
  determined in Plan 5 by capturing official `netinstall-cli` talking to `ni-sim`.
- Official tool uses *raw* BOOTP and NETINSTALL sockets on Linux, with fallback to normal sockets.
  pyNetinstall works on real hardware with plain UDP broadcast, so Plan 2 starts with plain UDP.
- Devices send Netinstall frames with **source IP 0.0.0.0**; the server receives its own
  broadcasts, so filter by source MAC.
- pyNetinstall cannot run on macOS unmodified (Linux-only `SIOCGIFHWADDR` ioctl), so the
  "validate ni-sim against pyNetinstall" idea from the spec is replaced by: ni-sim is written from
  pyNetinstall's code, and validated against the official `netinstall-cli` in Plan 5.
- Toolchain: rustup stable (1.99.1) is installed in `~/.cargo/bin`, but MacPorts' Rust 1.71 comes
  first in `PATH`. Plan 1 Task 0 handles this.

## Open hardware checks (from Plan 1 review)

- **Same-seq de-duplication:** `ServerSession` re-sends unanswered frames with the same `seq`
  (pyNetinstall never does). Verify a real board ignores a duplicated chunk — send one chunk twice
  on purpose. If it does not de-duplicate, disable retransmits for chunk steps
  (`ni-sim` `SimConfig::dedup = false` test shows the corruption mode).
- **Replies after the last chunk:** we require two state-matched replies, the second `RETR`
  (mirrors pyNetinstall). Capture what a real board actually sends.
- **Seq wraparound:** plans over 65535 frames (~64 MiB) are rejected; verify on hardware before lifting.

## Plan 2 outline — Network servers

- `ni-net`: list interfaces (name, MAC, IPv4/mask, up) via `getifaddrs` (`nix` crate);
  `Transport` trait; macOS `UdpTransport` using `socket2` with `SO_BROADCAST`, `SO_REUSEADDR`/`SO_REUSEPORT`
  and `IP_BOUND_IF` (setsockopt level `IPPROTO_IP`, option 25) on a tokio `UdpSocket`.
- `ni-bootp`: parse BOOTP/DHCP requests (op, htype, chaddr, xid, option 60, option 93);
  reply with yiaddr from a MAC-keyed pool, siaddr = server IP, file = per-arch boot filename;
  handle both plain BOOTP and DHCPDISCOVER/REQUEST (OFFER/ACK); reply to `255.255.255.255:68`.
- `ni-tftp`: RFC 1350 RRQ, `blksize` (RFC 2348) and `tsize` (RFC 2349) options, per-transfer
  ephemeral socket, retransmit on timeout, read-only file map.
- Tests: codec unit tests with byte fixtures; loopback integration tests (client implemented in test).

## Facts established during Plan 2 (2026-11-06)

- Unprivileged processes can bind UDP 67, 69 and 5000 on macOS; no root needed for the servers.
- `IP_BOUND_IF` is `socket2::Socket::bind_device_by_index_v4` (socket2 0.6.5, feature `all`).
  A wildcard (`0.0.0.0`) socket bound to `lo0` still receives unicast to 127.0.0.1.
- `lo0` cannot send to `255.255.255.255` (`ENETUNREACH`), so broadcast replies cannot be
  tested on loopback: `ni_bootp::serve` takes the reply destination as a parameter.
- nix 0.31 `LinkAddr::addr()` does not check the address length; `ni-net` checks `alen() == 6`.
- No `Transport` trait yet: the runners take a `tokio::net::UdpSocket`. The engine (Plan 4)
  owns sockets; a trait is added only if a BPF transport is ever needed.
- Review fixes (2026-11-06): `BindOptions::reuse` defaults to **false** — listeners on :67/:69/:5000
  must not set `SO_REUSEPORT`, or they would silently share the port with another server that does;
  without it any holder is reported as `AddrInUse`. `recv_from` errors in both runners follow
  `ni_net::RecvErrorGuard` (ICMP errors, `ENOBUFS`, `EINTR`, … back off 20 ms and are reported at
  most once per second; other errors, or 100 transient errors in a row, end the server). The BOOTP responder serves direct-link clients only (relayed requests are
  ignored), NAKs requests for foreign addresses and quarantines a declined lease (only a MAC holding
  a lease, with option 54 naming us, can decline). Config rejects a pool outside the subnet, a pool
  with no usable address and a server IP that is the network/broadcast address.

## Open hardware checks (from Plan 2)

- Broadcast BOOTP reply out of an `IP_BOUND_IF` socket reaches the board (and only via that port).
- RouterBOOT TFTP client: which options it sends (`tsize`? `blksize`?), and that it boots with
  `honor_blksize = false` (default). Also check whether it retransmits RRQ.
- Whether RouterBOOT sends DHCP (option 53) or plain BOOTP, per arch; capture to pcap fixtures.
- **smips vendor class:** smips boards are assumed to send `Mips_boot` (mapped to `BootArch::Mips`);
  unverified — capture option 60 from a real smips board.
- **Option 60 exact bytes:** capture the raw vendor class bytes per arch (trailing NUL? padding?).
  We strip trailing NULs/whitespace and otherwise match exactly.
- **DATA source IP:** transfer sockets now bind `server_ip:0` so DATA comes from the address the
  RRQ was sent to; check whether RouterBOOT rejects DATA from any other source IP (and port rules).
- **`bootpd` / launchd `tftpd` reuse behaviour:** check whether macOS `bootpd` (Internet Sharing)
  and the launchd `tftpd` set `SO_REUSEPORT`, and that our no-reuse listeners on :67/:69 report
  `AddrInUse` while they run.

## Plan 3 outline — Assets

- Version resolution: `https://upgrade.mikrotik.com/routeros/NEWESTa7.<channel>` (`stable`, `long-term`, `testing`), returns `<version> <timestamp>`.
- Downloads: `https://download.mikrotik.com/routeros/<ver>/netinstall-<ver>.tar.gz` and
  `…/routeros-<ver>-<arch>.npk` (+ extra packages; package list from `all_packages-<arch>-<ver>.zip`).
  Exact URL patterns are verified with HEAD requests as the first task of Plan 3.
- Kernel extraction per the table above; cache in `~/Library/Caches/<bundle-id>/<version>/`.
- NPK verification: magic `0x1EF1D0BA` (first 4 bytes, from pyNetinstall), size; SHA-256 recorded in cache index.
- Device arch string → package arch mapping table (unknown → explicit error).

## Facts established during Plan 3 (2026-11-06)

- Version check: `https://upgrade.mikrotik.com/routeros/NEWESTa7.<channel>` for `stable`,
  `long-term`, `testing` and `development`; body `<version> <unix time>\n`
  (e.g. `7.25.1 1793623193`). `testing` equals `stable` while no rc is out. Unknown channel → 404.
- Downloads (`https://download.mikrotik.com/routeros/<ver>/…`): `netinstall-<ver>.tar.gz`,
  `<name>-<ver>-<arch>.npk` (main package `routeros`; the old `routeros-<arch>-<ver>.npk` order
  serves the same file; `routeros-<ver>.npk` without arch is x86), `all_packages-<arch>-<ver>.zip`.
  Extra packages are also published one by one under the same name pattern. Missing files → 404.
- Checksums: `<file>.sha256` (`sha256sum` format) exists for every file of 7.16.2 and later;
  7.12.1 and older have none (404). `ni-assets` verifies against it when present and records
  `published_checksum` in the cache index.
- NPK header: magic `1E F1 D0 BA` + `u32` LE length; file size is always length + 8 (7.1 … 7.25.1).
- The extra-package list comes from the zip's central directory via `Range: bytes=-65536`
  (the server answers 206); no need to download the zip.
- reqwest 0.13's `rustls` feature uses aws-lc-rs and `rustls-platform-verifier` (macOS trust
  store). reqwest 0.13 needs Rust 1.85 and sha2 0.11 needs 1.88, so the workspace MSRV is 1.88.
- 7.25.1 kernels carve to: mips 5256784, mmips 5358860, powerpc 5486936, e500 6119156,
  ppc440 5709072, arm 3501676, arm64 7838328, tile 4680160 bytes (SHA-256s in
  `crates/ni-assets/tests/network.rs`).

## Open hardware checks (from Plan 3)

- Exact `arch` strings in the Netinstall hello per device family. `PkgArch::from_device_arch`
  accepts `arm`, `arm64`, `mipsbe`, `mmips`, `smips`, `ppc`/`powerpc`, `tile` (case-insensitive);
  x86 is reported as unsupported.
- Each carved kernel boots its family; especially the PowerPC split (generic / e500 / 440 by the
  `Linux version` suffix) and smips boards on the `Mips` kernel.

## Plan 4 outline — Engine + CLI

- tokio runtime; one task owns transport + BOOTP + TFTP + all `ServerSession`s (demux by src MAC).
- Event stream (`tokio::sync::broadcast`) with codes + params (no localized text).
- Profiles (JSON in Application Support), concurrency limit, auto-repeat with cooldown.
- Preflight checks (interface IP in pool subnet, port conflicts e.g. `bootpd`, assets ready).
- `ni-cli` with `clap`; first real-hardware test as soon as a device is available.
- Runner APIs needed by the engine (from the Plan 2 review):
  - query and modify leases and the arch → boot-file map while the BOOTP runner is running
    (today both are fixed at `BootpResponder::new`);
  - a MAC allow/deny policy hook for BOOTP/TFTP: post-flash cooldown (do not re-boot a device that
    was just flashed) and a concurrency limit;
  - TFTP progress events (`Transfer::acked_bytes`, throttled), not only start/complete/fail;
  - IP → MAC correlation, so a TFTP peer (IP only) and the Netinstall session (MAC) can be matched
    to the BOOTP lease;
  - bounded or rate-limited event channels instead of `UnboundedSender` (a flood of junk
    datagrams must not grow memory without limit);
  - interface type info in `ni-net` (Ethernet vs Wi-Fi / `awdl` / `utun` / bridges) so the UI can
    hide interfaces that cannot boot a router.
- Preflight: check `TftpConfig { server_ip, interface }` and `BootpConfig::server_ip` are consistent
  (the IP is configured on that interface, listeners bound to the same interface).
